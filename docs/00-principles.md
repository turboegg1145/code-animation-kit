# 00 · 原理：为什么每一帧都必须是纯函数
这套工具链交付的不是一段视频，是**一段能重跑的代码**。片子只是它的一次输出。

核心契约只有一行：
```js
frame(n, width, seed) -> 一张图
```
同一个 `(n, width, seed)` 永远得到同一张图。没有「上一帧」，没有全局时间，没有累积状态。

`assets/skeleton.html` 里对外的唯一接口是 `window.RISO.frame()`：
```js
window.RISO.frame(n, width, seed)   // 渲染第 n 帧，返回 canvas.toDataURL('image/png')
```
内部实现是 `renderFrame`：
```js
function renderFrame(n, width, seed, target)
```
`n` 是全局帧号（内部会对 `TOTAL()` 取模回绕），`width` 是输出像素宽，`seed` 换一整套随机流，`target` 是「画到哪块画布」。**除了这四个参数，它不读任何外部状态**：不读时钟、不读 `Math.random()`、不读上一帧留下的变量。
## 1. 三个好处
### 1.1 可以 seek
任何一帧都能单独渲染，不必从第 0 帧跑过来。
```bash
node assets/shot.mjs 0 60 120          # 只要这 3 帧 -> shots/f00000.png f00060.png f00120.png
W=960 OUT=/tmp/look node assets/shot.mjs 522     # 24 秒片的 17.4s 处，改一下宽度重看
```
* 拉片（联系表）靠这个能力成立：24 格 = 全片均匀撒 24 个采样点，每格独立渲染。
* `SHEET_FROM` / `SHEET_TO` / `START` / `END` 可以框任意窗口：只重渲被改过的那 90 帧。
* `RESUME=1` 断点续渲：渲到一半断电，重启后已存在的帧直接跳过，**而且跳过不会改变它们的像素**。
* 交付评审时可以把「第 417 帧我要看细节」变成一个 3 秒的操作，而不是一次全片重渲。

反例：如果第 n 帧依赖第 n−1 帧，那么第 522 帧只能从第 0 帧一路推过来——seek 就不存在了。
### 1.2 逐帧渲染不受单帧耗时影响
实时渲染里，「这一帧算得慢」会直接变成掉帧、节奏错乱。离线逐帧渲染里没有这条因果链：一帧花 1.3 秒，它在时间轴上还是那一帧。

本机实测（WSL2 / 4 核 / 页面内 `performance.now()` 包 `window.RISO.frame()`，含 `toDataURL` 的 PNG 编码）：

| 场景（1920×1080） | 单帧耗时 |
|---|---|
| 骨架演示分镜，`S.post.grain` / `S.post.vig` 开着（颗粒 2/9、暗角 0.10/0.34） | 468–713 ms |
| 同一份代码，把两处 `S.post.grain` / `S.post.vig` 置 0 | 52–80 ms |
| 成品 24 秒片 `film/index.html` | 421–586 ms（phos 段自渲染联系表那一帧 1316 ms） |
结论：**贵的是逐像素后处理，不是画图形**。这条实测直接决定了工作方式——先把构图做对，最后再开颗粒和暗角。
### 1.3 确定性可复现
* 音频侧有硬证据：`node assets/audio.mjs` 连跑两次，WAV 的 md5 都是 `ba8faee94012d56b3c49862f52831b34`。
* 画面侧靠纪律：`hash()` / `rng()` 代替 `Math.random()`，随机流掺段落名（见 01），Chrome 带 `--disable-accelerated-2d-canvas`。
* 实际收益：改了 3 秒处的一个字，不用担心 20 秒处跟着变；改完可以把「改动后的 6 帧」单独提出来给人看。
* **多标签页并行是安全的**：`render.mjs` 默认开 4 个标签页抢帧，谁先空谁取下一帧，结果与取帧顺序无关。这是纯函数白送的能力，不是额外工程。
## 2. 代价：你不能「记得上一帧」

| 想这么写 | 为什么坏 | 改写成 |
|---|---|---|
| `x += v; y += v;` | 每帧累加 = 依赖函数被调用的次数，seek 一次就错位 | `x = x0 + v * S.i` |
| 粒子数组 `parts.push(...)` 后遍历更新 | 状态跨帧累积，第一帧和第七百帧的数组长度不同 | 每个粒子位置写成闭式：`p = p0 + v*t + 0.5*a*t*t`；粒子自己的随机数用 `rng(hash(seed,'p',i))` |
| 拖尾：整帧盖一层 `g.globalAlpha=0.9` | 这是拿「上一帧的输出」当输入 | 在 `t - k*dt` 把物体重画 6–10 次（见 3.1） |
| `Math.random()` | 不可复现 | `R`（整段固定）/ `S.b`（每 3 帧重掷）/ `S.nz`（每帧重掷） |
| `Date.now()`、`performance.now()` | 不可复现 | 只用 `S.f` / `S.i` / `S.t` |
| 把上一帧结果缓存进闭包 | 顺序依赖，换个标签页就变 | 需要「历史」就把它写成 t 的闭式 |
| 真反馈（读回画布像素当下一帧输入） | 顺序依赖 | 改成固定次数的解析迭代（例如固定 2 次的高斯近似），或者干脆不做 |
| 靠 `requestAnimationFrame` 的 `dt` 驱动 | 依赖真实帧率 | 用 `S.i` 与 `FPS` 算时间 |
对「不能用累积状态」的另一种说法：**动画里的一切都必须是时间的函数，而不是历史的函数。**
## 3. 把「记得过去」的效果改写成 t 的函数
### 3.1 拖尾 / 运动模糊：在过去的若干时刻重画
```js
const samples = 8, span = 0.06;                 // 等价于 60 ms 的快门
for (let i = samples - 1; i >= 0; i--) {
  g.globalAlpha = Math.pow(1 - i / samples, 2); // 越旧的子帧越淡
  drawObj(g, t - i * span / samples);           // 在「过去」的某一刻画同一个物体
}
g.globalAlpha = 1;
```
6–10 个采样就够；采样数就是快门长度与清晰度的旋钮。骨架里终端段那种「字烧成方块飞散」就是每个方块按闭式抛物线位移 + 取 3 个子帧做运动模糊。
### 3.2 手绘沸腾：让驱动它的随机数换得比帧率慢
```js
// S.b = rng(hash(seed,'b',name,Math.floor(n/3)))：每 3 帧换一次抖动相位
const jittered = boil(linePts, S.b, 3.2);   // 3 帧内线不动，第 4 帧整体换一个抖法
```
这是「手绘感」在代码里最省的做法：不是让线每帧乱抖（那是噪点），而是每 3 帧换一个整体偏移（那是手抖）。
### 3.3 回弹 / 弹簧：闭式解，不积分
骨架里的签名（`assets/skeleton.html`）：
```js
function spring(t, zeta = 0.42, omega = 15) {
  if (t <= 0) return 0;
  const wd = omega * Math.sqrt(1 - zeta * zeta);
  return 1 - Math.exp(-zeta * omega * t) * (Math.cos(wd * t) + (zeta * omega / wd) * Math.sin(wd * t));
}
```
* `t <= 0` 返回 0，`t` 大时趋近 1 —— 天然是一个「从 0 到 1 的入场」。
* 它是**解析解**：给定 t 直接算位置，不需要上一帧的位移和速度。这就是「弹簧」能在纯函数引擎里存在的原因。
* 调研笔记里的参考版本是 `zeta=0.45, omega=14`；骨架里落地的是 `0.42/15`。用哪个都行，**但一部片子里保持一致**。
### 3.4 真物理：只能按固定 dt 推，两个体面的折衷
流体、布料、刚体这类东西没有闭式解，只能逐帧积分——那就**放弃 seek**（或者接受「只能从头渲」）。

两个折衷：

1. **预烘表**：离线跑一次模拟，把每 N 帧的位置烘成一个数组字面量塞进 HTML，运行时按 `t` 插值。文件变大，但可 seek、可复现。
2. **解析近似**：用弹簧 + 阻尼正弦 + 抛物线去「演」物理。绝大多数风格化短片里看不出区别，成本却是零。

真需要精确流体，就换工具。这不是这套流程的强项，硬做只会两头不讨好。
## 4. 时间轴纪律：三个帧号别搞混

| 变量 | 含义 | 用途 |
|---|---|---|
| `S.f` | 全局帧号 `n` | 时间码、每帧噪声、跨段对齐 |
| `S.i` | 段内局部帧（`0 .. S.len-1`） | **段内动画的唯一时间轴** |
| `S.t` | 段内进度 `0..1`（`S.i / S.len`） | 与段落长度无关的归一化进度 |
| `S.len` | 本段总帧数 | 归一化、循环 |
最常踩的坑（真实发生过）：把全局量减在局部帧上。
```js
const T0 = at('phos', 0);                     // 全局帧：570
stagger(S.i - (T0 + SHEET_IN), ...)           // S.i 是局部帧（0..149）→ 得到 -542
```
表达式恒为 0，整段动画不出现，而且**不报错**。

规矩：**跨段对齐用 `at('名字', 拍数)` 拿全局帧；段内只用 `S.i`。**
```js
function at(name, x = 0)      // -> 全局帧号：'名字' 段起点 + x 拍（找不到会 throw）
function cue(name)            // -> 全局帧号：CUES 里登记的提示点，画面和声音共用
```
## 5. 确定性纪律（工程层，每一条都能毁掉「可复现」）
* Chrome 必须带 `--disable-accelerated-2d-canvas`（`render.mjs` / `shot.mjs` 已经带上）。加速画布在几次 readback 之后会退回软件光栅，同一个帧在新标签页和用过的标签页里像素不同——症状是「同一帧在不同标签页颜色不一样」。
* 取像素用 `canvas.toDataURL()`，**不要用 `page.screenshot()`**。截图受 CSS、设备像素比、视口影响；`toDataURL` 返回的是画布上真实的像素。
* 不读 `Math.random()`、`Date.now()`、`performance.now()`、`window.innerWidth`：宽度走参数（`?w=` / `W=`），种子走 `?s=` / `SEED=`。
* 中文字体必须装（`fc-list :lang=zh`）。canvas 画不出字时**不报错**，直接空白。
* 段落随机流掺段落名：`hash(seed,'plate',name)` / `hash(seed,'b',name,Math.floor(n/3))` / `hash(seed,'nz',n)`。插一段、删一段都不会平移其它段的随机数。
* 不在 `renderFrame` 里 `await` 任何东西（字体加载交给启动时的 `document.fonts.ready`）。
## 6. 和「AI 生成视频」的区别

| | 这套流程 | 模型直出视频 |
|---|---|---|
| 像素从哪来 | 你写的代码画的 | 模型采样出来的 |
| 改一个像素 | 改代码，重渲这一帧 | 重新生成，整段都变 |
| 精确到帧 | 是（`frame(n, …)`） | 通常不是 |
| 可重跑 | 同参数逐字节一致 | 不可 |
| 单次成本 | 一次全片渲染（720 帧 @1920 约 3.5 分钟） | 一次生成 |
| 迭代方式 | 静帧 → 拉片 → 改代码 | 重掷骰子 |
| 风格来源 | 你给的约束（调色板、画幅、字体、时长） | 提示词 + 模型先验 |
| 强项 | 文字、构图、节奏、可精确控制的运动 | 写实材质、流体、光照 |
| 弱项 | 写实材质、流体、复杂光照 | 精确的文字、可复现性、可编辑性 |
顺带说清楚来路：2025 年底刷屏的那些「某某模型直出视频」，绝大多数也不是视频生成——是模型写了一个会自己动的网页，再一帧一帧拍成视频。这个仓库把那套流程里跟题材无关的部分抽出来做成了工具。

**关键差别是最后一行**：你的每一次修改都是改代码，而不是重新掷骰子。
## 7. 边界（别硬撑）
* 适用：10–90 秒、风格化 > 写实（铜版画、像素画、瑞士海报、终端、蓝图、半调网点、数据可视化镜头）。
* 不适用：写实视频、真人素材剪辑、需要精确对白的口播。
* 超过 2 分钟要慎重：720 帧 @1920 已经约 3.5 分钟；2 分钟 = 3600 帧，渲染时间按比例涨。
* 文字是强项（毕竟是在写代码画字），复杂物理 / 写实材质是弱项。
* 配乐另算：`assets/audio.mjs` 是纯 Node 手写加法合成（见 04）。
## 8. 怎么证明你的片子真是纯函数（三个实验）
**实验 A：同一帧渲两次，比 md5**
```bash
cd /home/eggdog/项目/code-animation-kit
node assets/shot.mjs 0 60 120 && md5sum shots/f00000.png shots/f00060.png
node assets/shot.mjs 0 60 120 && md5sum shots/f00000.png shots/f00060.png
# 两行必须完全一致
```
**实验 B：seek 一致性（乱序渲染不改变像素）**
```bash
SEED=7 OUT=/tmp/seekA node assets/shot.mjs 120 0 60      # 乱序
SEED=7 OUT=/tmp/seekB node assets/shot.mjs 0 60 120      # 顺序
cmp /tmp/seekA/f00060.png /tmp/seekB/f00060.png && echo "seek 一致"
```
**实验 C：并行一致性（多标签页只影响顺序，不影响像素）**
```bash
HTML=assets/skeleton.html START=0 END=30 node assets/render.mjs /tmp/par1 7 960 1
HTML=assets/skeleton.html START=0 END=30 node assets/render.mjs /tmp/par2 7 960 4
for n in $(seq -w 0 29); do cmp -s /tmp/par1/f000$n.png /tmp/par2/f000$n.png || echo "第 $n 帧不一致"; done
```
三个实验都过，才谈得上「这套片子是可以 re-render 的」。
## 动手前的检查清单

| 检查项 | 合格线 |
|---|---|
| 代码里是否出现 `Math.random` / `Date.now` / `performance.now` | 一次都不能有 |
| 是否有变量在帧之间被写（`+=`、`push`、闭包缓存） | 没有 |
| 段内动画是否只用 `S.i` / `S.t` | 是 |
| 跨段对齐是否走 `at()` / `cue()` | 是，不许写死帧号 |
| 随机流是否都掺了段落名 | `hash(seed,'plate',name)` 之类 |
| 拖尾/运动模糊是否用「重画过去若干时刻」实现 | 是，不是盖一层半透明 |
| Chrome 参数是否带 `--disable-accelerated-2d-canvas` | 是（用仓库里的脚本就是） |
| 取帧是否走 `toDataURL` | 是 |
| 实验 A / B / C 是否通过 | 全过 |
